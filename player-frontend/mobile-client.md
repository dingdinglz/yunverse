# 虚拟乐器演奏项目手机客户端文档（React Native）

## 1. 文档概述

本文档说明虚拟乐器演奏项目手机客户端的设计。手机客户端使用 React Native 开发，核心功能是让用户选择乐器和音调，并通过演奏按钮向后端发送播放请求。后端收到请求后会结合戒指手势解析出的技法，播放对应 WAV 声音。

手机客户端不直接播放最终乐器音频，也不直接处理戒指手势。手机客户端负责提供清晰、低延迟的演奏入口，并把用户选择的乐器、音调和音符准确发送给后端。

## 2. 产品目标

手机客户端的目标是提供一个简单可靠的虚拟乐器控制面板。用户打开 App 后，可以看到演奏按钮，选择当前乐器和音调，然后点击按钮触发后端发声。

本期核心目标包括：展示 do、ri、mi、fa、so、la、xi、do 演奏按钮；支持乐器切换，首期包括吉他和琵琶；支持音调切换，覆盖 C、D、E、F、G、A、B 及升降号变体；点击按钮后向后端发送请求；展示请求状态和错误提示；保存最近一次选择的乐器和音调。

## 3. 功能范围

手机客户端包含演奏主界面、乐器选择、音调选择、后端连接配置、演奏反馈和基础错误提示。

演奏主界面展示当前乐器、当前音调和演奏按钮。乐器选择允许用户在吉他和琵琶之间切换。音调选择允许用户选择 C、D、E、F、G、A、B 以及 C#、Db、D#、Eb、F#、Gb、G#、Ab、A#、Bb 等升降号变体。演奏反馈用于告诉用户请求是否已发送、是否成功触发播放。后端连接配置用于在开发或演示环境中填写后端服务地址。

## 4. 页面结构

手机客户端建议采用单页主操作界面。顶部展示连接状态和当前后端地址。中部展示当前乐器、当前音调，并提供切换入口。底部展示演奏按钮区。

页面布局建议如下：

```text
┌──────────────────────────┐
│ 连接状态：已连接           │
│ 后端：192.168.1.10:8080   │
├──────────────────────────┤
│ 当前乐器：琵琶   [切换]    │
│ 当前音调：D      [切换]    │
├──────────────────────────┤
│ [do] [ri] [mi] [fa]       │
│ [so] [la] [xi] [do]       │
├──────────────────────────┤
│ 最近演奏：琵琶 / D / so    │
│ 状态：播放请求成功         │
└──────────────────────────┘
```

用户需求中提到“七个按钮”，同时列出了 do ri mi fa so la xi do。这里包含低音 do 到高音 do 的八个音级。为了符合演奏习惯，本文档建议界面展示八个按钮，最后一个 do 在数据层标识为 `do_high`。如果产品最终确认必须只有七个按钮，则移除 `do_high`，保留 do、ri、mi、fa、so、la、xi。

## 5. 技术架构

React Native 客户端建议采用组件分层架构，包括页面层、组件层、状态层、服务层和配置层。

页面层负责组合整体界面。组件层包括乐器选择器、音调选择器、音符按钮、连接状态条和提示组件。状态层维护当前乐器、音调、后端地址、请求状态和最近演奏信息。服务层封装 API 请求。配置层维护枚举常量和默认值。

推荐技术选择为 React Native、TypeScript、React Hooks、AsyncStorage 和 Fetch API。若项目后续复杂度提高，可以引入 Zustand、Redux Toolkit 或 React Query。

## 6. 模块说明

### 6.1 App 启动模块

App 启动模块负责初始化配置，包括读取本地保存的后端地址、最近选择的乐器和音调。若本地没有记录，则默认乐器为吉他，默认音调为 C。

启动后可以调用后端健康检查接口 `GET /api/v1/health`，确认服务是否可用。如果连接失败，页面应显示未连接状态，但不阻塞用户修改后端地址。

### 6.2 演奏主界面模块

演奏主界面是用户最常使用的页面。它展示当前乐器、当前音调和音符按钮。用户点击音符按钮时，页面会调用演奏服务发送请求。

该模块需要保证按钮响应足够快。点击后可以立即显示“请求发送中”，收到后端响应后显示“播放请求成功”或错误提示。不要在按钮点击后进行复杂计算，避免影响演奏手感。

### 6.3 乐器选择模块

乐器选择模块提供吉他和琵琶两个选项。内部数据标识建议为 `guitar` 和 `pipa`，展示文案为吉他和琵琶。注意乐器名称应写作“琵琶”，不要写作“枇杷”。

切换乐器后，应立即更新页面状态，并保存到本地存储。后续点击按钮时使用最新乐器值发送请求。

### 6.4 音调选择模块

音调选择模块提供标准音名和升降号变体。建议默认选项包括 C、C#、Db、D、D#、Eb、E、F、F#、Gb、G、G#、Ab、A、A#、Bb、B。

如果后端通过配置接口返回可用音调列表，客户端应优先使用后端返回值。这样可以避免客户端展示后端没有音频资源的音调。

### 6.5 音符按钮模块

音符按钮模块负责展示按钮并响应点击。每个按钮绑定一个 `note` 编码。建议按钮数据如下：

| 展示名 | note 编码 | 说明 |
| --- | --- | --- |
| do | do | 1 级音 |
| ri | ri | 2 级音 |
| mi | mi | 3 级音 |
| fa | fa | 4 级音 |
| so | so | 5 级音 |
| la | la | 6 级音 |
| xi | xi | 7 级音 |
| do | do_high | 高音 1 级音 |

点击按钮时，客户端发送 `instrument`、`key` 和 `note`。技法由后端根据戒指手势确定，客户端不需要发送技法。

### 6.6 API 服务模块

API 服务模块封装所有 HTTP 请求，包括健康检查、获取配置和触发演奏。该模块统一处理后端地址、超时、JSON 序列化、错误码和响应解析。

演奏请求接口为 `POST /api/v1/play`。请求示例：

```json
{
  "instrument": "pipa",
  "key": "D",
  "note": "so"
}
```

响应示例：

```json
{
  "success": true,
  "data": {
    "eventId": "evt_20260723224300001",
    "instrument": "pipa",
    "key": "D",
    "note": "so",
    "technique": "normal",
    "played": true
  }
}
```

### 6.7 本地存储模块

本地存储模块保存用户常用配置。建议保存 `backendBaseUrl`、`selectedInstrument` 和 `selectedKey`。存储可以使用 `@react-native-async-storage/async-storage`。

保存数据时应使用明确 key，例如 `virtualInstrument.backendBaseUrl`。读取失败时使用默认值，并在日志中记录失败原因。

## 7. 数据结构

### 7.1 Instrument

```ts
export type InstrumentCode = 'guitar' | 'pipa';

export interface Instrument {
  code: InstrumentCode;
  name: string;
}
```

示例数据：

```ts
export const instruments: Instrument[] = [
  { code: 'guitar', name: '吉他' },
  { code: 'pipa', name: '琵琶' },
];
```

### 7.2 KeySignature

```ts
export type KeySignature =
  | 'C'
  | 'C#'
  | 'Db'
  | 'D'
  | 'D#'
  | 'Eb'
  | 'E'
  | 'F'
  | 'F#'
  | 'Gb'
  | 'G'
  | 'G#'
  | 'Ab'
  | 'A'
  | 'A#'
  | 'Bb'
  | 'B';
```

### 7.3 Note

```ts
export type NoteCode = 'do' | 'ri' | 'mi' | 'fa' | 'so' | 'la' | 'xi' | 'do_high';

export interface NoteButton {
  code: NoteCode;
  label: string;
}
```

### 7.4 PlayRequest

```ts
export interface PlayRequest {
  instrument: InstrumentCode;
  key: KeySignature;
  note: NoteCode;
}
```

### 7.5 PlayResponse

```ts
export interface PlayResponse {
  success: boolean;
  data?: {
    eventId: string;
    instrument: InstrumentCode;
    key: KeySignature;
    note: NoteCode;
    technique: string;
    played: boolean;
  };
  error?: {
    code: string;
    message: string;
  };
}
```

## 8. 关键流程

### 8.1 首次打开 App

用户首次打开 App 时，客户端读取本地配置。如果没有配置，则使用默认后端地址、默认乐器吉他和默认音调 C。随后客户端发起健康检查请求。如果后端可用，页面展示已连接；如果后端不可用，页面展示未连接，并允许用户修改后端地址。

### 8.2 切换乐器

用户点击乐器切换入口后，页面展示乐器列表。用户选择吉他或琵琶后，客户端更新状态并写入本地存储。下一次演奏请求会使用新的乐器。

### 8.3 切换音调

用户点击音调切换入口后，页面展示音调列表。用户选择 C、D、E、F、G、A、B 或升降号变体后，客户端更新状态并写入本地存储。下一次演奏请求会使用新的音调。

### 8.4 点击音符按钮

用户点击音符按钮后，客户端立即构造请求并调用后端接口。请求发送期间按钮可以保持可点击，也可以短暂禁用。为了更接近真实演奏，本期建议不全局禁用按钮，只对被点击按钮展示短暂加载反馈。

后端返回成功后，客户端展示最近演奏信息。后端返回失败时，客户端展示错误原因，例如后端未连接、音频资源不存在或播放设备不可用。

## 9. 错误处理

手机客户端需要处理网络不可达、请求超时、参数错误、后端错误和音频资源缺失。网络不可达时提示“无法连接后端，请检查后端地址和网络”。请求超时时提示“请求超时，请检查后端服务”。音频资源缺失时提示“当前乐器、音调或技法的音频资源未配置”。

错误提示应简洁，不要展示复杂堆栈信息。开发模式下可以在控制台输出完整错误，便于排查。

## 10. 交互与体验要求

演奏按钮应足够大，适合快速点击。按钮布局建议两行显示，按钮之间保留足够间距，避免误触。当前乐器和音调应在页面明显位置展示，让用户点击前能确认当前配置。

点击反馈应轻量，可以使用按钮缩放、颜色变化或短暂高亮。请求成功不建议弹出阻塞式弹窗，否则会影响连续演奏。错误才需要更明显提示。

## 11. 开发建议

项目建议使用 TypeScript，并为 API 请求、枚举配置和关键组件编写单元测试。演奏主界面可以使用 mock API 先完成 UI 联调，再接入真实后端。

目录结构建议如下：

```text
src/
  components/
    InstrumentSelector.tsx
    KeySelector.tsx
    NoteButtonGrid.tsx
    ConnectionStatus.tsx
  screens/
    PlayScreen.tsx
  services/
    apiClient.ts
    playService.ts
  storage/
    preferences.ts
  types/
    instrument.ts
    play.ts
  constants/
    instruments.ts
    keys.ts
    notes.ts
```

## 12. 测试用例

客户端测试应覆盖默认配置加载、乐器切换、音调切换、按钮点击请求体、后端成功响应、后端错误响应和网络异常。特别需要验证琵琶名称展示正确，音调升降号可以正确发送，例如 `C#` 和 `Bb` 不应被错误转义或丢失。

## 13. 后续扩展

后续可支持音量控制、节拍器、录制回放、用户自定义按钮布局、多设备选择、蓝牙戒指连接状态展示和 WebSocket 实时状态同步。如果客户端未来需要直接连接戒指，也应保持戒指逻辑独立封装，避免污染演奏主界面。
