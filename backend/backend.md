# 虚拟乐器演奏项目后端文档

## 1. 文档概述

本文档说明虚拟乐器演奏项目的后端设计。后端的核心职责是接收手机客户端的演奏请求，结合七个音符按钮、音调、乐器和戒指手势识别出的技法，选择并播放对应的 WAV 音频文件。同时，后端需要向电脑网站前端提供当前演奏状态和历史记录查询能力。

后端不直接负责手机客户端 UI，也不负责电脑网站页面展示。后端负责统一的演奏控制、音频资源管理、手势技法解析、播放执行、状态记录和 API 输出。

## 2. 背景与目标

虚拟乐器演奏项目由手机客户端、电脑网站前端、后端服务和戒指硬件组成。手机客户端提供七个演奏按钮和乐器、音调切换入口。戒指硬件通过手势提供技法输入。后端将这些输入合成为一次完整的演奏事件，并播放对应声音。

后端目标包括：支持低延迟播放单次 WAV 声音；支持乐器、音调、音符和技法组合；支持戒指手势到技法的映射；提供当前状态和历史记录接口；保证音频资源命名、查找、缺失处理和播放流程可维护。

## 3. 业务范围

后端本期支持手机客户端触发演奏请求。每次请求包含乐器、音调和音符信息。后端接收请求后读取当前戒指手势状态，解析出技法，然后选择对应 WAV 文件播放一次。

本期乐器支持吉他和琵琶。音调支持标准音名 C、D、E、F、G、A、B，以及升号和降号变体，例如 C#、Db、D#、Eb、F#、Gb、G#、Ab、A#、Bb。七个演奏按钮对应 do、ri、mi、fa、so、la、xi，其中高音 do 作为第八个音级在接口中可表示为 do_high，UI 上仍显示为 do。

戒指手势到技法的规则由额外文档提供。后端文档中先定义技法解析模块的输入输出和扩展方式，具体映射规则详见手势说明文档（待补充）。

## 4. 总体架构

后端采用分层架构，建议拆分为 API 接入层、业务编排层、手势技法层、音频资源层、播放执行层、状态与历史层。

API 接入层负责接收手机客户端和电脑网站前端请求，进行参数校验、认证预留、错误返回和响应封装。业务编排层负责把一次演奏请求转换为完整演奏事件。手势技法层负责读取戒指手势状态并转换成技法。音频资源层负责根据乐器、音调、音符和技法定位 WAV 文件。播放执行层负责调用系统音频能力播放一次 WAV。状态与历史层负责保存当前状态和最近演奏记录，供电脑网站前端展示。

一次典型演奏链路为：手机客户端点击按钮，向后端发送演奏请求；后端校验乐器、音调和音符；后端读取当前戒指手势；后端将手势解析成技法；后端根据乐器、音调、音符和技法查找 WAV 文件；后端播放该 WAV 一次；后端更新当前状态并追加历史记录；后端向客户端返回本次演奏结果。

## 5. 模块说明

### 5.1 API 接入模块

API 接入模块提供 HTTP JSON 接口。它负责接收请求、解析 JSON、校验字段、统一错误码和返回结构。该模块不包含音频播放细节，也不直接理解戒指手势规则。

主要接口包括演奏触发接口、当前状态查询接口、历史记录查询接口、枚举配置查询接口和健康检查接口。详细接口定义见 `docs/api.md`。

### 5.2 演奏编排模块

演奏编排模块是后端核心模块。它接收 API 层传入的演奏请求，组装演奏上下文，并按照固定顺序执行：参数归一化、读取手势、解析技法、选择音频、执行播放、记录状态、生成响应。

该模块需要保证一次请求只播放一次声音。如果同一用户快速连续点击按钮，后端可以按请求到达顺序播放，也可以在后续版本中加入队列、节流或覆盖策略。本期建议使用轻量串行播放队列，避免多个 WAV 同时播放造成声音重叠不可控。

### 5.3 戒指手势与技法模块

戒指手势与技法模块负责接入硬件状态。它的输入可以是戒指 SDK 推送、蓝牙网关上报、串口数据或独立硬件服务接口。后端内部应将不同来源统一转换成标准 `GestureState` 数据结构。

技法解析输出为 `Technique`。例如后续可以支持拨弦、扫弦、滑音、颤音、泛音等技法。具体手势到技法的映射规则不在本文档展开，详见手势说明文档（待补充）。

该模块建议提供默认技法。当没有戒指连接、手势状态过期或无法识别时，后端应使用默认技法 `normal`，保证手机客户端点击按钮仍能发声。

### 5.4 音频资源模块

音频资源模块负责维护 WAV 文件的索引和查找逻辑。推荐按乐器、音调、技法和音符组织目录，例如：

```text
audio/
  guitar/
    C/
      normal/
        do.wav
        ri.wav
        mi.wav
        fa.wav
        so.wav
        la.wav
        xi.wav
        do_high.wav
  pipa/
    D/
      normal/
        do.wav
```

乐器目录建议使用英文稳定标识，吉他为 `guitar`，琵琶为 `pipa`。对外展示名称使用中文。音调目录使用标准音名，升号建议使用 `sharp` 或 URL 安全写法，例如 `C_sharp`；降号建议使用 `D_flat`。接口层可以接收 `C#` 和 `Db`，音频资源层负责转换成文件系统安全路径。

当目标 WAV 不存在时，后端应返回明确错误，并记录缺失资源信息。可选兜底策略是退回到同乐器、同音调、默认技法 `normal` 的音频；若仍不存在，则返回错误。

### 5.5 播放执行模块

播放执行模块负责在服务器或连接音响的主机上播放 WAV 文件。它应隐藏具体平台差异，例如 Linux 可对接 ALSA、PulseAudio 或 PipeWire；macOS 可调用系统播放器；嵌入式设备可对接专用音频库。

播放接口建议设计为同步确认、异步播放。也就是说，业务层调用播放模块后，播放模块确认任务已提交即可返回，实际声音播放由播放线程或队列执行。这样可以减少 HTTP 请求阻塞时间。

### 5.6 状态与历史模块

状态与历史模块保存当前演奏状态和历史记录。当前状态包括当前乐器、当前音调、当前技法、最近音符、最近播放时间和设备连接状态。历史记录包括每次演奏的请求参数、解析后的技法、音频文件路径、播放结果和时间戳。

本期可以使用内存存储，满足单机演示和开发调试。后续如果需要多设备、多用户或长时间审计，可以扩展为 SQLite、PostgreSQL 或 Redis。

## 6. 数据结构

### 6.1 Instrument

`Instrument` 表示乐器。

| 字段 | 类型 | 示例 | 说明 |
| --- | --- | --- | --- |
| code | string | guitar | 稳定标识，用于接口和音频资源路径 |
| name | string | 吉他 | 中文展示名称 |
| enabled | boolean | true | 是否可用 |

本期支持的乐器为 `guitar` 和 `pipa`，展示名称分别为吉他和琵琶。

### 6.2 KeySignature

`KeySignature` 表示音调。

| 字段 | 类型 | 示例 | 说明 |
| --- | --- | --- | --- |
| code | string | C# | 对外接口使用的标准音名 |
| pathCode | string | C_sharp | 文件路径安全标识 |
| displayName | string | C# | UI 展示名称 |

支持 C、D、E、F、G、A、B 以及升降号变体，包括 C#、Db、D#、Eb、F#、Gb、G#、Ab、A#、Bb。B#、Cb、E#、Fb 是否启用可按音乐理论和资源制作情况决定，建议接口保留扩展能力。

### 6.3 Note

`Note` 表示七个按钮触发的音级。

| 字段 | 类型 | 示例 | 说明 |
| --- | --- | --- | --- |
| code | string | do | 音符标识 |
| displayName | string | do | UI 展示文案 |
| degree | number | 1 | 调式内音级 |

按钮顺序建议为 do、ri、mi、fa、so、la、xi、do_high。用户需求中提到七个按钮，并列出 do ri mi fa so la xi do，这里存在“七个按钮”和“两个 do”之间的数量差异。实现时建议按八个音级处理，若产品最终确认必须只有七个按钮，则去掉 `do_high`。

### 6.4 Technique

`Technique` 表示技法。

| 字段 | 类型 | 示例 | 说明 |
| --- | --- | --- | --- |
| code | string | normal | 技法标识 |
| name | string | 普通演奏 | 中文展示名称 |
| sourceGesture | string | gesture_001 | 来源手势标识 |

具体技法列表和手势映射详见手势说明文档（待补充）。

### 6.5 GestureState

`GestureState` 表示戒指当前手势状态。

| 字段 | 类型 | 示例 | 说明 |
| --- | --- | --- | --- |
| deviceId | string | ring-001 | 戒指设备 ID |
| gestureCode | string | gesture_001 | 硬件识别出的手势编码 |
| confidence | number | 0.93 | 识别置信度，范围 0 到 1 |
| timestamp | string | 2026-07-23T22:43:00+08:00 | 手势产生时间 |
| connected | boolean | true | 戒指是否连接 |

### 6.6 PlayEvent

`PlayEvent` 表示一次完整演奏事件。

| 字段 | 类型 | 示例 | 说明 |
| --- | --- | --- | --- |
| eventId | string | evt_20260723224300001 | 演奏事件 ID |
| instrument | string | pipa | 乐器标识 |
| key | string | D | 音调 |
| note | string | so | 音符 |
| technique | string | normal | 技法 |
| audioPath | string | audio/pipa/D/normal/so.wav | 实际播放文件 |
| status | string | played | 播放状态 |
| createdAt | string | 2026-07-23T22:43:00+08:00 | 创建时间 |

## 7. 关键流程

### 7.1 手机按钮触发播放流程

用户在手机客户端选择乐器和音调后点击某个按钮。手机客户端向后端发送 `POST /api/v1/play` 请求，请求中包含 `instrument`、`key` 和 `note`。后端接收请求后首先校验字段是否合法，然后读取最近一次有效戒指手势。若手势可用，后端根据映射规则得到技法；若手势不可用，后端使用默认技法 `normal`。之后，后端定位 WAV 文件并提交播放任务。播放任务提交成功后，后端写入当前状态和历史记录，并返回本次事件 ID 与播放结果。

### 7.2 戒指手势更新流程

戒指硬件通过约定通道上报手势状态。后端接收手势数据后转换为标准 `GestureState`，并更新当前设备状态。技法解析不一定在手势上报时完成，也可以在演奏请求到达时实时解析。为了降低播放延迟，建议在手势上报时预计算当前技法，并在播放请求中直接读取最近的有效技法。

### 7.3 音频查找流程

后端根据乐器、音调、技法和音符生成候选路径。第一优先级是完整匹配路径，例如 `audio/pipa/D/normal/so.wav`。如果该路径不存在，可以尝试默认技法路径。若仍不存在，返回 `AUDIO_NOT_FOUND`。后端应记录缺失路径，方便音频资源补齐。

### 7.4 状态同步流程

电脑网站前端通过轮询或 WebSocket 获取当前状态。简单版本可以每 1 秒调用 `GET /api/v1/state` 和 `GET /api/v1/history`。后续如果需要更实时的体验，可以扩展 WebSocket，将每次演奏事件主动推送到网站前端。

## 8. 配置设计

后端应将乐器、音调、音符、技法、音频根目录和播放设备配置化。推荐配置项包括 `audio.rootDir`、`playback.device`、`playback.queueMode`、`gesture.expireMs`、`history.maxSize` 和 `server.port`。

示例配置如下：

```json
{
  "server": {
    "port": 8080
  },
  "audio": {
    "rootDir": "audio"
  },
  "playback": {
    "device": "default",
    "queueMode": "serial"
  },
  "gesture": {
    "expireMs": 1000,
    "fallbackTechnique": "normal"
  },
  "history": {
    "maxSize": 100
  }
}
```

## 9. 异常处理

后端需要对参数错误、资源缺失、戒指未连接、播放失败和内部错误分别返回清晰错误。参数错误返回 `400`，资源缺失返回 `404`，播放设备不可用返回 `503`，内部错误返回 `500`。

戒指未连接不应阻断播放。后端应使用默认技法并在响应中通过 `warnings` 字段提示。音频资源缺失应阻断播放，因为没有可播放文件。播放失败需要记录系统错误信息，但响应中不应暴露过多机器路径或系统细节。

## 10. 性能与可靠性要求

后端应尽量降低从手机点击到声音发出的延迟。建议目标为本地网络下 100 毫秒到 300 毫秒内提交播放任务。音频文件索引应在服务启动时加载，避免每次请求都进行大量磁盘扫描。播放队列应避免无限堆积，可以设置最大队列长度。

历史记录写入不应影响播放主链路。如果使用数据库，建议异步写入或使用轻量缓存。当前状态应始终保留最近一次成功或失败的演奏事件，便于网站前端展示。

## 11. 安全与权限

开发阶段可以使用局域网无鉴权模式。正式使用时建议加入简单设备令牌，例如 `X-Device-Token`，用于区分手机客户端、网站前端和硬件网关。后端应限制跨域来源，避免同一局域网内未知网页随意触发播放。

## 12. 开发与测试建议

后端测试需要覆盖参数校验、音频路径生成、手势到技法解析、播放任务提交、历史记录写入和错误返回。可以使用 mock 播放器替代真实音频设备，保证自动化测试稳定。

建议准备一组最小音频资源，例如吉他 C 调 normal 技法的 do 到 do_high，以及琵琶 D 调 normal 技法的 do 到 do_high。这样可以优先打通完整链路，再逐步补齐其他音调和技法资源。

## 13. 后续扩展

后续可扩展多用户、多戒指、多乐器、多声部、WebSocket 实时推送、MIDI 输出、音量控制、节拍器和录制回放。若项目从演示版进入产品化阶段，建议引入持久化数据库和设备管理后台。
