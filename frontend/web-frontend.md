# 虚拟乐器演奏项目电脑网站前端文档

## 1. 文档概述

本文档说明虚拟乐器演奏项目的电脑网站前端设计。电脑网站前端主要用于展示当前演奏状态，包括当前乐器、当前音调、当前技法，以及类似历史记录的演奏事件列表。它是观察和调试演奏系统状态的桌面端界面，不直接负责发声。

电脑网站前端面向演示、调试和状态监控场景。用户可以通过它确认手机客户端发送的请求是否到达后端，戒指手势是否解析为正确技法，以及后端是否成功播放对应音频。

## 2. 产品目标

电脑网站前端的目标是让演奏状态一眼可见。页面打开后，应清晰展示当前乐器、当前音调、当前技法、最近演奏音符、最近播放时间和系统连接状态。页面还应展示历史记录，帮助用户回看最近的演奏事件。

本期不要求电脑网站前端提供演奏按钮，也不要求直接控制乐器和音调。它的重点是展示和追踪。后续如果需要，也可以增加手动触发播放、清空历史和导出记录等能力。

## 3. 功能范围

本期功能包括当前状态展示、历史记录展示、后端连接状态展示、自动刷新、错误提示和基础配置。

当前状态展示包括乐器、音调、技法、音符和播放状态。历史记录展示包括事件时间、乐器、音调、音符、技法和播放结果。自动刷新可以通过轮询实现，默认每 1 秒刷新一次。错误提示用于展示后端不可用、接口请求失败或数据格式异常。

## 4. 页面信息架构

电脑网站前端建议采用单页仪表盘布局。顶部为系统标题和连接状态，中间为当前状态卡片，底部为历史记录表格。

推荐布局如下：

```text
┌──────────────────────────────────────────────┐
│ 虚拟乐器演奏控制台                  已连接     │
├──────────────────────────────────────────────┤
│ 当前乐器        当前音调        当前技法         │
│ 琵琶            D               普通演奏         │
├──────────────────────────────────────────────┤
│ 最近音符        播放状态        最近播放时间     │
│ so              成功            22:43:00         │
├──────────────────────────────────────────────┤
│ 历史记录                                      │
│ 时间       乐器   音调   音符   技法   结果      │
│ 22:43:00   琵琶   D      so     普通   成功      │
└──────────────────────────────────────────────┘
```

## 5. 技术架构

电脑网站前端可以使用 React、TypeScript 和 Vite 实现。状态管理可以先使用 React Hooks；若后续功能复杂，可以引入 Zustand 或 Redux Toolkit。接口请求可以使用 Fetch API 或 Axios。

前端架构建议分为页面层、组件层、服务层、类型层和样式层。页面层负责整体布局，组件层负责当前状态卡片和历史记录表格，服务层封装后端 API，类型层定义接口数据结构，样式层统一视觉风格。

## 6. 模块说明

### 6.1 Dashboard 页面模块

Dashboard 页面是网站唯一主页面。它负责加载当前状态和历史记录，并将数据传递给各个展示组件。页面应在加载时立即请求一次后端数据，然后按固定间隔自动刷新。

如果后端不可用，Dashboard 应展示未连接状态，并保留最近一次成功获取的数据。这样演示时即使后端短暂不可达，也不会导致页面完全空白。

### 6.2 当前状态卡片模块

当前状态卡片展示系统当前状态。建议拆分为乐器、音调、技法、最近音符、播放状态和最近播放时间六个信息块。

乐器展示使用中文名称，例如吉他、琵琶。音调展示使用标准音名，例如 C、D、F#、Bb。技法展示使用后端返回的中文名称；如果后端只返回技法 code，前端可以通过枚举映射展示名称。若技法未知，展示“未知技法”。

### 6.3 历史记录模块

历史记录模块展示最近的演奏事件。表格字段建议包括时间、乐器、音调、音符、技法、播放结果和事件 ID。默认展示最近 50 条记录。

历史记录应按时间倒序排列，最新记录在最上方。播放成功可以用绿色状态标识，播放失败可以用红色状态标识。若后端返回 warnings，例如戒指未连接并使用默认技法，前端可以在结果列展示提示图标。

### 6.4 后端连接状态模块

连接状态模块负责展示后端是否可用。它可以调用健康检查接口 `GET /api/v1/health`，也可以根据状态和历史接口是否请求成功来判断。

连接状态建议包括已连接、连接中、未连接三种。已连接表示最近一次请求成功；连接中表示正在请求；未连接表示请求失败或超时。

### 6.5 API 服务模块

API 服务模块封装当前状态、历史记录、枚举配置和健康检查接口。所有接口请求都应设置超时时间，避免页面长时间卡在加载状态。

建议 API 基础地址通过环境变量配置，例如 `VITE_API_BASE_URL=http://localhost:8080`。开发环境默认连接本机后端，演示环境可配置为局域网后端地址。

## 8. 关键流程

### 8.1 页面初始化流程

用户打开电脑网站后，前端读取 API 地址配置。页面先显示加载状态，然后并行请求健康检查、当前状态和历史记录。请求成功后，页面展示当前状态和历史表格。请求失败时，页面展示未连接状态和错误提示。

### 8.2 自动刷新流程

页面初始化完成后，前端启动定时器，每 1 秒请求一次当前状态和历史记录。为了减少请求量，历史记录可以每 2 到 3 秒刷新一次，当前状态保持 1 秒刷新。后续如改为 WebSocket，可由后端主动推送演奏事件，前端收到事件后更新当前状态和历史列表。

### 8.3 历史记录更新流程

当前端拿到新的历史记录后，应按 `eventId` 或 `createdAt` 去重并排序。如果后端返回完整列表，前端可以直接替换当前列表。如果后端返回增量事件，前端需要将新事件插入列表顶部，并限制最大展示数量。

### 8.4 错误恢复流程

如果某次请求失败，前端不应清空已有数据。页面应保留最近一次成功数据，并将连接状态标记为未连接。下一次请求成功后，连接状态恢复为已连接。

## 9. 视觉与交互要求

电脑网站前端应适合横屏展示。当前状态卡片要足够醒目，便于演示时远距离查看。历史记录表格要保持紧凑，避免一屏只能看到少量记录。

颜色建议保持克制。连接成功用绿色，连接失败用红色，请求中用蓝色或灰色。乐器、音调和技法可使用大字号展示。历史记录中的播放失败项应突出显示。

## 10. 接口依赖

电脑网站前端依赖以下后端接口：健康检查接口 `GET /api/v1/health`，当前状态接口 `GET /api/v1/state`，历史记录接口 `GET /api/v1/history`，枚举配置接口 `GET /api/v1/config`。接口定义详见 `docs/api.md`。

如果后端暂时没有实现配置接口，前端可以使用本地默认枚举。乐器默认包括吉他和琵琶。音调默认包括 C、C#、Db、D、D#、Eb、E、F、F#、Gb、G、G#、Ab、A、A#、Bb、B。

## 12. 测试建议

前端测试应覆盖页面初始化、接口成功、接口失败、连接状态变化、历史记录排序、空状态展示和错误提示。需要特别验证琵琶展示文字正确，升降号音调可以正常显示，技法为空或未知时页面不会崩溃。

开发时可以准备 mock 数据，模拟吉他、琵琶、不同音调、不同技法、播放成功和播放失败。这样在后端未完成时也能独立开发网站前端。

## 13. 后续扩展

后续可以加入 WebSocket 实时推送、手势状态可视化、音频资源缺失提示、历史记录筛选、导出 CSV、暗色模式和演示大屏模式。如果项目需要多人协作调试，还可以加入设备列表和会话维度。
